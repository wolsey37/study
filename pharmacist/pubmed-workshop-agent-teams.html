01 · 5분

개념과 차이

한 문장으로: 일 시킨 담당끼리 서로 말을 걸 수 있게 된 것입니다. 그게 전부입니다.

쉽게 말하면

둘 다 일을 맡기는 것인데, 맡긴 뒤가 다릅니다.

서브에이전트 = 외주 일을 맡기고 결과만 받습니다. 외주끼리는 서로 모릅니다. scout의 결과를 miner에게 주려면 메인이 들고 갑니다.

에이전트 팀 = 같이 일하는 직원 옆자리에 앉아 있습니다. scout이 miner에게 바로 넘깁니다. 메인은 보고만 받고, 한 명만 따로 부를 수도 있습니다.

그림으로 보면

서브에이전트

＋싸고 단순합니다. 일이 끝나면 결과가 알아서 메인에 옵니다

－담당끼리 못 엮습니다. 메인이 전부 나릅니다

－끝나면 사라집니다. 다시 물으려면 처음부터

에이전트 팀

＋담당끼리 직접 주고받습니다. 메인을 안 거칩니다

＋끝나도 이름이 살아 있어 이어서 물을 수 있습니다 (메인 세션이 떠 있는 동안만 — 세션이 끝나면 이름도 함께 사라집니다)

－각자 별도 세션이라 토큰을 더 씁니다

－결과가 자동으로 안 옵니다 — 직접 보내야 합니다

왼쪽은 화살표가 전부 메인으로 향합니다. sub A가 찾은 것을 sub B에게 주려면 메인이 받아서 다시 넘기는 수밖에 없습니다. 오른쪽은 서로에게 닿습니다 — 다만 직접 붙어 있는 것은 아닙니다. 가운데를 거쳐 가고, 그 가운데가 메인이 아닙니다.

그 가운데가 Shared Task List와 Mailbox입니다. 메시지를 보내면 상대의 Mailbox에 쌓이고, 상대가 그것을 읽습니다. Mailbox가 곧 주소라서, 이름이 없으면 보낼 데가 없습니다.

같은 담당 파일을 쓰더라도 이렇게 다릅니다
　서브에이전트 (지난 시간)에이전트 팀 (오늘)
서로 대화못 합니다이름을 불러 직접 메시지
결과 전달끝나면 자동으로 메인에게안 옵니다 — 「끝났다」는 알림만 옵니다.
보내라고 시켜야 옵니다
끝난 뒤사라짐 — 다시 물으려면 처음부터끝나도 이름이 살아 있음 — 부르면 그 대화 그대로 깨어남
(단, 메인 세션이 살아 있는 동안만 — 세션 종료 시 함께 소멸, 영구 보존 아님)

같은 일을 두 방식으로 시켜보면

A · 서브에이전트

메인이 나릅니다

① evidence-scout 서브에이전트로 마그네슘 수면 논문 지형을 훑어줘. → 끝나면 결과가 자동으로 옵니다 PMID 4개 · 톤 T3 · 논문별 intervention 판정 ② 그 PMID 4개로 abstract-miner 를 돌려서 숫자를 뽑아줘. → PMID를 메인이 직접 들고 넘깁니다 → miner 가 「34211088이 마그네슘 단독인가 복합제인가」 궁금해도 scout 은 이미 사라졌습니다 → 초록만 보고 추측하게 됩니다
B · 에이전트 팀

담당끼리 주고받습니다

① 에이전트 팀으로 실행해줘. evidence-scout 으로 scout 을 띄우고, 결과 JSON은 SendMessage 로 나한테 보내라고 해줘. → finished 알림만 옵니다 「보내라」고 시켜야 내용이 도착합니다 ② abstract-miner 로 miner 를 띄워줘. PMID 마다 scout 한테 판정을 물어보라고 해줘. → miner ──→ scout 「34211088 뭐로 판정했나?」 miner ←── scout 「Mg+B6 복합제. 단독 아님」 → scout 은 ①에서 끝났지만, 이름을 부르면 그 대화 그대로 깨어납니다

서브에이전트는 메인이 나르고, 팀은 담당끼리 주고받습니다. 대신 팀은 결과가 저절로 오지 않아 보내라고 시켜야 합니다.

담당 둘이면 Claude가 셋 도는 셈입니다. 다만 일할 때만 씁니다. 끝난 담당은 부를 때까지 아무 비용도 쓰지 않습니다. 그러니 켜둔 것 자체는 문제가 아니고, 같은 주제를 여러 번 돌린 것이 비용이 됩니다.

02 · 5분

사용법

여기서는 담당 하나를 띄워 조작해 보는 것까지만 봅니다. 전체를 도는 것은 03입니다. 버튼은 없습니다. 전부 말로 시킵니다.

설정 ① — 기능 켜기 (기본은 꺼져 있습니다)

아직 실험 기능이라 직접 켜야 합니다. 이걸 안 켜면 담당에 이름이 붙지 않고, 이름이 없으면 서로 부를 수도 없습니다. 둘 중 아무 쪽이나 하시면 됩니다.

말로 시키기

에이전트 팀 기능을 켜줘. ~/.claude/settings.json 의 env 에 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS 를 "1" 로 넣어줘. 기존 설정은 지우지 말고 그 항목만 추가해줘.

직접 넣기 — ~/.claude/settings.json

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
껐다 켤 필요 없습니다. 저장하면 돌고 있는 세션에 바로 반영됩니다.

설정 ② — 담당마다 창 나누기 (선택)

담당들은 기본적으로 한 화면 안에 목록으로 뜹니다. 담당마다 창을 갈라 동시에 보고 싶을 때만 설정을 하나 더 넣습니다 — 안 넣어도 되니 건너뛰셔도 됩니다.

~/.claude/settings.json 에 넣는 값
teammateMode언제 창이 갈리나필요한 것
"in-process" (기본값) 갈리지 않음 — 메인 터미널 한 화면 안에 전부 아무 터미널이나. 추가 설치 없음
"auto" tmux 세션 안이거나 iTerm2를 쓸 때만 갈림. 아니면 한 화면으로 되돌아갑니다 tmux 또는 iTerm2
"tmux" 항상 갈림 — tmux와 iTerm2 중 무엇을 쓸지는 알아서 고릅니다 tmux 또는 iTerm2
"iterm2" 항상 갈림 — iTerm2 방식으로 못 박습니다 iTerm2 (it2 명령 필요)

tmux 나 iTerm2 를 따로 깔아야 합니다. VS Code 내장 터미널·Windows Terminal·Ghostty 에서는 안 됩니다. 다만 안 된다고 못 하게 되는 일은 없습니다 — 화면만 다르고 되는 일은 같습니다.

담당 하나를 띄워봅니다

이렇게 지시합니다

이걸 에이전트 팀으로 실행해줘. evidence-scout 으로 담당 하나 띄워줘, 이름은 scout. 마그네슘 × 수면으로 논문 지형을 훑어봐.

한 줄씩 뜯어보면

evidence-scout = 업무 매뉴얼 그 일을 어떻게 하는지 적어둔 파일입니다. 지난 시간에 만들어 뒀고, 오늘 고치지 않습니다.

scout = 이름표 오늘 그 일을 맡은 담당에게 붙이는 이름입니다. 이름표가 있어야 나중에 「scout아」 하고 부를 수 있습니다.

매뉴얼은 하나여도 이름표는 여럿 붙일 수 있습니다 — 같은 evidence-scout 으로 scout1·scout2 를 동시에 띄우는 것도 됩니다.

띄우면 입력창 아래에 나타납니다

● main ← 여러분이 말을 걸던 그 Claude ○ scout 작업 중··· ← 방금 띄운 담당

이 목록에서 이렇게 움직입니다.

  • ↑ ↓ — 담당을 고릅니다
  • Enter — 고른 담당 화면으로 들어갑니다. 거기서 타자를 치면 메인이 아니라 그 담당에게 갑니다
  • Esc — 하던 일을 멈춥니다  /  x — 아예 정지시킵니다

한 명에게 직접 말을 걸어봅니다

↑↓로 scout을 고르고 Enter를 누릅니다. 그 화면에 그대로 칩니다.

그 담당 화면에서 이렇게

지금 걸린 것 중에 off_target 이 절반이 넘네. 성분명이 너무 넓은 것 같으니 균주 단위로 좁혀서 다시 봐줘.

이건 미리 시킬 수 없는 지시입니다. 검색 결과를 봐야 off_target이 많은 줄 알 수 있으니까요. 도는 중에 화면에 들어가 방향을 트는 것 — 이게 팀원과 서브에이전트가 갈리는 곳입니다.

「그건 서브에이전트도 되지 않나」 — 안 됩니다. 서브에이전트는 일하는 중에 말을 걸 수 없습니다. 진행 상황을 보거나 멈추는 것까지고, 끝나야 결과를 받습니다. 방향을 틀려면 끝날 때까지 기다렸다 처음부터 다시 시켜야 합니다. 반면 처음부터 알 수 있는 지시(「가이드라인도 검색해라」 같은)는 애초에 소집 프롬프트에 넣으면 됩니다. 굳이 끼어들 일이 아닙니다.

03 · 핵심 · 2분

위임 구조

.claude/commands/진행.md 파일 하나입니다. 이 파일이 정하는 것은 위임 구조 하나뿐이고, 판단 기준과 검증 규칙은 전부 기존 파일에 그대로 둡니다.

이 한 줄로 아래 전부가 돕니다

/진행 마그네슘 수면

필요할 때 한 명씩

P1 정규화 (메인이 직접) ↓ ① scout 을 띄운다 → 검색·판정 → SendMessage로 JSON ↓ 그 JSON이 곧 채굴 요청서다 ② miner 를 띄운다 → PMID를 손에 쥐고 태어나 채굴 │ │ PMID 한 편마다 │ miner ──→ scout "PMID 34211088 뭐로 판정했나?" │ miner ←── scout "Mg+B6 복합제 / off_target 권고" │ ↓ SendMessage로 배열 P6 검증 (스크립트) → evidence-pack.json ← 지난 시간 것 그대로 scout 은 끝났지만 사라지지 않았습니다. 이름을 부르면 그 대화 그대로 다시 깨어나 답합니다.
미리 띄워두지 않는 이유는 간단합니다. 미리 띄우든 나중에 띄우든 채굴이 시작되는 시점은 scout이 끝난 뒤로 같습니다. 먼저 띄우면 기다리게 할 방법을 찾아야 하고, 그동안 비용과 화면 소음만 붙습니다.

안 멈추는 것을 막습니다

  • 조회 실패한 PMID는 1회만 다시. 두 번째도 실패하면 그대로 두고 넘어감
  • 폐기된 슬롯을 다시 뽑아오게 시키지 말 것 — 이름을 부르면 되니 유혹이 큽니다
  • 재검색은 사람이 요청할 때만. 빈약해 보인다고 검색어를 바꾸지 않음

「폐기된 걸 다시 뽑아줘」가 제일 위험합니다. 폐기는 정상 동작입니다. 통과시키려 애쓰는 순간 검증이 무의미해집니다.

팀으로 만들 수 있다고 해서
팀처럼 써야 하는 건 아닙니다.

04 · 3분

활용

담당을 순서대로 부르는 것은 팀이 아니어도 됩니다. 끝난 담당이 이름으로 남아 있다는 것 — 그것만이 팀의 몫입니다. 그 이름으로 무엇을 할 수 있는지 둘을 놓았습니다.

하나

miner → scout 되묻기

둘 다 떠 있을 때 눈으로 확인해 볼 수 있습니다. ↑↓로 miner를 고르고 Enter로 들어가서, 그 화면에 직접 칩니다.

miner 화면에서

scout 한테 PMID 34211088 을 뭐로 판정했는지 물어봐줘.

miner 화면에 찍히는 것

→ [scout] PMID 34211088 판정 조회 ← [scout] PMID 34211088 = Mg+B6 복합제 / off_target 권고

scout 화면으로 옮겨가면

← [miner] PMID 34211088 판정 조회 받음 → [miner] PMID 34211088 = Mg+B6 복합제 / off_target 권고

같은 교신이 양쪽에 찍히고 화살표 방향만 반대입니다. 화살표와 대괄호가 표식이라 다른 로그와 섞이지 않습니다. 메인 화면에는 이 두 줄이 안 뜹니다 — 둘 사이에서만 오간 것이라서요.

왜 팀이어야 하나 — scout은 이미 끝났습니다. 서브에이전트였다면 그 판정과 함께 사라져 물어볼 데가 없습니다.

둘

메인 → 끝난 miner 다시 부르기

결과를 받아 보다가 미심쩍은 대목이 나왔을 때. 커맨드를 처음부터 다시 돌릴 필요가 없습니다.

이렇게 지시합니다

miner 한테, 34211088 이거 하나만 다시 봐달라고 해줘.

왜 팀이어야 하나 — 이름을 부르면 그 대화 그대로 깨어납니다. 자기가 뭘 뽑았는지 기억한 채로 답하니, 다시 설명할 필요가 없습니다.

반대로, 이런 일에는 팀이 필요 없습니다. 앞사람 결과를 뒷사람에게 넘기기만 하면 되는 일, 한 번 시키고 끝나는 일. 되묻거나 다시 부를 일이 없다면 그냥 시키는 게 빠르고 쌉니다.

팀을 쓰는 기준은 하나입니다.
끝난 담당을 다시 부를 일이 있는가.
